## 架构设计

### 四层架构（单写模型）

```
Layer 4: API 层        - WalManager, WalBuilder
Layer 3: 协调层        - WriteCoordinator, ReadCoordinator, RecoveryManager
Layer 2: 组件层        - LogWriter, LogReader, SegmentCoordinator
Layer 1: 存储层        - Storage trait, FileStorage, MemoryStorage
```

### 核心组件

| 组件 | 说明 |
|------|------|
| `WriteCoordinator` | 单写入协调器，处理同步策略和段轮转 |
| `ReadCoordinator` | 读取协调器，支持预读优化 |
| `SegmentCoordinator` | 段轮转策略决策 |
| `RecoveryManager` | 崩溃恢复和检查点管理 |
| `SyncStrategy` | 同步策略（None/Batch/Periodic/FsyncOnWrite） |

### 并发模型说明

**本 WAL 采用单写入点设计**，理由如下：

1. **WAL 的本质**: 日志必须是串行化的有序流，多写最终还是要合并
2. **业界实践**: RocksDB、PostgreSQL、MySQL 等主流 WAL 都是单写入点
3. **性能最优**: Group Commit 已解决核心问题（合并 fsync），外部队列更灵活
4. **架构简单**: 减少复杂度，便于理解和维护

**用户需要高并发写入时**，推荐在应用层实现：

```rust
// 多生产者 + 单消费者模式
let (tx, mut rx) = tokio::sync::mpsc::channel(1000);

// 多个生产者写入 channel
for i in 0..10 {
    let tx = tx.clone();
    tokio::spawn(async move {
        tx.send(data).await.unwrap();
    });
}

// 单一消费者写入 WAL（避免锁竞争）
tokio::spawn(async move {
    while let Some(data) = rx.recv().await {
        wal.write(&data).await?;
    }
});
```

这种设计：
- ✅ WAL 保持简单清晰
- ✅ 用户可根据场景选择队列类型（mpsc/mpmc、有界/无界）
- ✅ 可以在应用层优化批量拉取策略
- ✅ 符合"组合优于继承"的原则

## 开发原则

1. **简单优先** - 优先选择简单的方案，避免过度设计
2. **性能导向** - 每个决策考虑性能影响，用基准测试验证
3. **测试驱动** - 新功能必须有测试覆盖
4. **教学价值** - 代码清晰易懂，便于学习
5. **业界对齐** - 参考主流 WAL 设计（RocksDB/PostgreSQL）
6. **数据完整性** - 宁可性能损失，也要保证数据不丢失
